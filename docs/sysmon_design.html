SysMon 설계 — Multi-AMR AED 관제 화면

화면 구성(UI 설계안) · 웹 페이지 구조 · DB 테이블 구조 · 기동에서 화면 반영까지의 적재 로직

전체 시스템 설계도(HW/SW 경계, 메시지 인터페이스, function flow)는 docs/multi_amr_aed_architecture.drawio 와 docs/multi_amr_aed_review_architecture.drawio 에 있습니다. 이 문서는 그중 SysMon 파트 내부만 확대한 것입니다.

1. 화면 구성 (UI 설계안)

관제실 화면 한 장에 모든 것이 들어갑니다. 창 크기가 바뀌어도 영역의 높이는 고정하고 영상 영역만 늘어납니다. 사건이 터졌을 때 운영자가 보던 자리가 흔들리면 안 되기 때문입니다.

영역보여주는 것어디서 오나갱신
① 상단 표시줄 서버·ROS 연결, 로봇 수, 마지막 수신 경과, 현재 시각 WebSocket 스냅샷0.25초
② 응급 배너 진행 중 사건, 경과 시간, 도착 예상, 목표 좌표, 재할당 배지 WebSocket 스냅샷0.25초 / 경과·ETA는 매초
③ 4분할 영상 웹캠 2 + 로봇 OAK-D 2. 검출 시 테두리 경보 MJPEG 스트림 + 스냅샷의 검출 수연속
④ 로봇 상태 속도·배터리·위치·방위, 통신/위치추정/Nav2/경로 플래그 WebSocket 스냅샷0.25초
⑤ 출동 이력 누적 통계와 지난 임무 표 SQLite (REST)5초

③ 영역은 숫자키 1~4 로 한 갈래만 크게 볼 수 있습니다. 같은 키나 Esc 로 4분할로 돌아옵니다. 4분할에서는 멀리 있는 검출 상자가 안 보이는데, 급할 때 마우스로 타일을 찾는 것보다 손이 먼저 가기 때문에 단축키를 먼저 뒀습니다.

사건이 없을 때도 ② 의 높이는 그대로입니다. 배너가 접히면 사건이 터질 때마다 아래 영상이 통째로 밀려 내려가, 운영자가 보던 자리를 다시 찾아야 합니다.

3. 기동 → 빈 DB → 적재 → 화면 반영

이 그림이 SysMon 파트의 핵심입니다. 서버가 뜨는 순간부터 화면에 숫자가 찍히기까지 무엇이 어떤 순서로 일어나는지, 그리고 같은 입력이 왜 두 갈래로 갈라지는지를 보여줍니다.

왜 갈랐나

로봇 위치는 10 Hz 로 들어옵니다. 그때마다 DB 에 쓰고 다시 읽으면 디스크가 병목이 되고, 화면은 0.25초마다 갱신되어야 하는데 그 왕복을 기다리게 됩니다. 그래서 지금 상태는 메모리에만 두고 WebSocket 으로 바로 내보냅니다.

반대로 이력은 서버가 죽어도 남아야 하고, 사후에 "그때 왜 늦었나"를 되짚는 근거입니다. 그래서 일어난 일만 DB 에 남깁니다. 로봇 표본은 그대로 넣으면 로봇 2대에 하루 172만 행이라 1초에 한 번으로 솎습니다.

화면의 두 숫자가 서로 다른 경로로 옵니다. 상단 배너의 경과 시간은 메모리에서, 하단 이력의 응답 시간은 DB 에서 옵니다. 같은 사건인데 경로가 다르므로, 둘이 어긋나 보이면 어느 쪽이 밀렸는지부터 봐야 합니다.

빈 DB 에서 시작해도 화면이 뜬다

CREATE TABLE IF NOT EXISTS 라서 파일이 없으면 만들고 있으면 그대로 씁니다. 행이 0 이어도 통계는 null 로 나가고 화면은 "기록 없음"을 그립니다. ROS 데이터가 아직 수신되지 않은 상태에서도 서버와 화면 자체는 정상적으로 시작하고 연결 대기 상태를 표시합니다.

4. DB 테이블 구조

키를 표마다 다르게 잡은 이유

표기본키왜
emergency_events자연키 event_id 검출 노드가 만든 id. DB 가 새로 매기면 현장 로그와 관제 기록을 못 맞춘다
mission_assignments복합키 mission_id + version 재할당은 새 임무가 아니라 같은 임무의 다음 판. 덮어쓰면 "robot1 이 먼저 갔다 실패했다"가 사라진다
mission_events대리키 id 재할당하면 en_route 가 두 번, 복구하면 또 나온다. 자연키가 없다
robot_samples대리키 id 표본에는 자연키가 없다
eta_records복합키 request_id + robot_id 재할당되면 로봇마다 한 건씩 남는다

uint8 을 숫자 그대로 넣지 않는다

DB 를 열어 3 만 있으면 그게 무슨 상태인지 코드를 봐야 하고, 상수가 중간에 추가돼 번호가 밀리면 과거 기록의 뜻이 바뀝니다. 그래서 이름 문자열로 넣습니다. 변환은 domain/enums.py 한 곳에서만 하고, 화면(TypeScript)도 같은 문자열을 쓰므로 오타는 컴파일 오류로 드러납니다.

5. 설계도와 코드 매칭

발표 때 디렉토리를 열어 놓고 이 표를 짚으면 됩니다.

설계도 블록코드맡은 것
② 스키마 · 빈 DBstore/schema.sql표 5개, 인덱스 6개, WAL
② 연결 · ④ 적재store/repository.pySQL 전부. 이 파일 밖으로 안 나간다
③ 기동main.py · context.pylifespan 으로 시작·종료를 짝지어 둔다
④ 수신 · 변환ros/bridge.py · ros/converters.pyrclpy 를 아는 유일한 곳
④ 인터페이스 이름ros/topics.py토픽 이름과 QoS. rclpy 없이도 import 된다
⑤ 갈림길context.py: on_robot / on_event / on_mission / on_eta_record메모리와 DB 로 동시에 보낸다
Ⓐ 메모리stream/live_state.py · stream/frames.py지금 상태. 오래된 표본은 통신 이상으로 뒤집는다
Ⓐ 송출stream/hub.py · api/live.py0.25초마다 방송
Ⓑ 조회api/history.py이력·통계 창구
③ 영상api/video.pyMJPEG
①~⑤ 화면frontend/src/components/layout · video · robot · mission
타입 정의domain/models.py ↔ frontend/src/types/telemetry.ts1:1. 한쪽을 고치면 다른 쪽도 고친다
domain/ 은 ROS 도 HTTP 도 모릅니다. aed_interfaces 를 import 하는 곳은 ros/ 뿐입니다. 그래서 도메인 계산은 ROS 실행 없이 단위 테스트할 수 있고, 리뷰할 때도 ROS 를 몰라도 읽힙니다. 이것이 이 구조의 유일한 주장입니다.
